% ====================== 1 ОБЩИЕ СВЕДЕНИЯ =================================
\tzsec{1}{Общие сведения}{tz:s1}

\tzsubsec{1.1}{Наименование системы}{tz:s1-1}
Полное наименование системы: веб-приложение для планирования задач с учётом их местоположения и временных параметров.

Краткое наименование системы: веб-приложение <<Планировщик маршрутов>>.

\tzsubsec{1.2}{Основания для проведения работ}{tz:s1-2}
Основанием для разработки информационной системы являются следующие документы:
\begin{compactlist}
  \item утвержденная тема выпускной квалификационной работы <<Разработка веб-приложения для планирования задач с учётом их местоположения и временных параметров>>;
  \item задание на выпускную квалификационную работу;
  \item основная профессиональная образовательная программа по направлению 09.03.01 <<Информатика и вычислительная техника>>, профиль <<Системная и программная инженерия>>.
\end{compactlist}

\tzsubsec{1.3}{Плановые сроки начала и окончания работы}{tz:s1-3}
Плановый срок начала работ по созданию веб-приложения <<Планировщик маршрутов>>~--- 01~февраля 2026~года.

Плановый срок окончания работ~--- 27~мая 2026~года.

\tzsubsec{1.4}{Источники и порядок финансирования}{tz:s1-4}
Разработка производится в рамках учебной деятельности на безвозмездной основе.
Прямое финансирование не предусмотрено.

\tzsubsec{1.5}{Порядок оформления и предъявления заказчику результатов работ}{tz:s1-5}
Результаты работы передаются заказчику в виде пояснительной записки к выпускной
квалификационной работе, исходного кода (репозиторий системы управления версиями
Git) и собранного дистрибутива: контейнерного образа серверной части и статической
сборки клиентской части.

Порядок предъявления системы, ее испытаний и окончательной приемки определен в
разделе~7 настоящего технического задания. Совместно с предъявлением системы
производится сдача комплекта документации согласно разделу~9.

\tzsubsec{1.6}{Состав используемой нормативно-технической документации}{tz:s1-6}
При разработке системы и создании проектно-эксплуатационной документации Исполнитель
должен руководствоваться требованиями следующих нормативных документов:
\begin{compactlist}
  \item ГОСТ 19.201-78 Единая система программной документации. Техническое задание. Требования к содержанию и оформлению;
  \item ГОСТ 19.701-90 Единая система программной документации. Схемы алгоритмов, программ, данных и систем. Условные обозначения и правила выполнения;
  \item ГОСТ 34.602-2020 Информационные технологии. Комплекс стандартов на автоматизированные системы. Техническое задание на создание автоматизированной системы;
  \item ГОСТ Р 7.0.100-2018 Библиографическая запись. Библиографическое описание. Общие требования и правила составления;
  \item спецификация требований к программному обеспечению (Software Requirements Specification, SRS) по методике К.~Вигерса.
\end{compactlist}

\tzsubsec{1.7}{Структура веб-приложения}{tz:s1-7}
Все наименования разделов веб-приложения являются условными и могут корректироваться
в ходе разработки. Структура веб-приложения:
\begin{tzdash}
  \item страница регистрации и аутентификации;
  \item главная страница со списком задач и картой;
  \item форма создания и редактирования задачи;
  \item панель импорта и экспорта перечня задач;
  \item панель параметров и запуска оптимизации маршрута;
  \item панель результатов оптимизации с пошаговым описанием маршрута.
\end{tzdash}

% ====================== 2 НАЗНАЧЕНИЕ И ЦЕЛИ =============================
\tzsec{2}{Назначение и цели создания системы}{tz:s2}

\tzsubsec{2.1}{Назначение системы}{tz:s2-1}
Система предназначена для автоматизированного построения оптимальной последовательности
выполнения задач с учетом географического положения точек, временных окон обслуживания
и длительности выполнения каждой задачи.

\tzsubsec{2.2}{Основные цели создания системы}{tz:s2-2}
Основными целями создания веб-приложения являются:
\begin{compactlist}
  \item сокращение времени ручного планирования маршрута с временными окнами;
  \item уменьшение числа нарушений временных окон за счет автоматизированной проверки допустимости;
  \item обеспечение доступности инструментов оптимизации маршрута для частных пользователей и малого бизнеса без коммерческой подписки.
\end{compactlist}

\tzsubsec{2.3}{Критерии достижения целей}{tz:s2-3}
Для реализации поставленных целей система должна решать следующие задачи:
\begin{compactlist}
  \item провести анализ предметной области, обосновать актуальность разработки;
  \item провести сравнительный анализ существующих программных решений и аналогов;
  \item определить целевую аудиторию и ее потребности;
  \item сформировать функциональные и нефункциональные требования к системе;
  \item выбрать алгоритм оптимизации маршрута с учетом временных окон;
  \item спроектировать архитектуру и модель данных системы;
  \item спроектировать пользовательский интерфейс;
  \item разработать серверную часть (REST API, бизнес-логику, репозитории);
  \item разработать клиентскую часть и интегрировать ее с картографическим сервисом;
  \item провести модульное и нагрузочное тестирование системы.
\end{compactlist}

% ====================== 3 ОБЪЕКТ АВТОМАТИЗАЦИИ ==========================
\tzsec{3}{Характеристика объекта автоматизации}{tz:s3}

Объект автоматизации~--- процесс планирования последовательности выполнения задач
пользователя в городской среде. В отсутствие специализированного программного
обеспечения планирование выполняется вручную; при увеличении числа задач трудоемкость
возрастает нелинейно, а вероятность нарушения временных ограничений увеличивается.
Целевая аудитория системы: частные пользователи, специалисты на выезде, курьеры малого
бизнеса, индивидуальные предприниматели.

\tzsubsec{3.1}{Существующее программное обеспечение}{tz:s3-1}
На момент разработки используется следующее программное обеспечение: операционная
система (Windows, macOS или Linux), веб-браузер, среда разработки Visual Studio Code,
система контейнеризации Docker, система управления версиями Git.

\tzsubsec{3.2}{Существующее техническое обеспечение}{tz:s3-2}
Разработка ведется на персональном компьютере со следующими характеристиками:
многоядерный процессор, оперативная память не менее 8~ГБ, твердотельный накопитель,
подключение к сети Интернет.

\tzsubsec{3.3}{Существующее нормативно-правовое обеспечение}{tz:s3-3}
Обработка и хранение пользовательских данных осуществляются с учетом требований
законодательства Российской Федерации в области защиты персональных данных.
Используемые внешние картографические сервисы применяются в соответствии с условиями
их лицензионных соглашений.

% ====================== 4 ТРЕБОВАНИЯ К СИСТЕМЕ ==========================
\tzsec{4}{Требования к системе}{tz:s4}

\tzsubsec{4.1}{Требования к системе в целом}{tz:s4-1}

\tzsubsubsec{4.1.1}{Требования к структуре и функционированию системы}
Система реализуется в виде клиент-серверного веб-приложения и включает следующие
подсистемы:
\begin{compactlist}
  \item подсистема хранения данных~--- хранение данных о пользователях, задачах и построенных маршрутах;
  \item подсистема аутентификации~--- регистрация, вход и обновление сессии пользователя;
  \item подсистема управления задачами~--- создание, редактирование, удаление, импорт и экспорт задач;
  \item подсистема геокодирования и построения матрицы расстояний~--- взаимодействие с внешним картографическим сервисом;
  \item подсистема оптимизации маршрута~--- вычисление оптимальной последовательности выполнения задач;
  \item подсистема визуализации~--- отображение маршрута на карте и пошагового плана.
\end{compactlist}

\tzsubsubsec{4.1.2}{Требования к режимам функционирования}
Для системы определены два режима функционирования: неавторизованный (просмотр
стартовой страницы с возможностью регистрации и входа) и авторизованный (полный доступ
к функциям). Основным является авторизованный режим. Режим функционирования~---
непрерывный, с допустимыми технологическими перерывами на обслуживание.

\tzsubsubsec{4.1.3}{Требования к численности пользователей и производительности}
Численность одновременно работающих пользователей~--- до 100. Время отклика интерфейса
не превышает 2~секунд при нагрузке до 5~запросов в секунду.

\tzsubsubsec{4.1.4}{Требования к надежности и сохранности информации}
Система должна сохранять работоспособность при кратковременной недоступности внешнего
картографического сервиса за счет кэширования результатов. Должна быть предусмотрена
возможность резервного копирования данных средствами используемой системы управления
базами данных. При корректном перезапуске аппаратных средств система должна
автоматически восстанавливать работоспособность. Пароли пользователей хранятся в виде
хэш-значений, передача данных осуществляется по защищенному протоколу HTTPS.

\tzsubsec{4.2}{Требования к дизайну веб-приложения}{tz:s4-2}
Интерфейс системы проектируется в минималистичном стиле, без перегруженности
графическими элементами. Дизайн должен быть адаптивным и обеспечивать корректное
отображение на устройствах с диагональю экрана от 4 до 32~дюймов (смартфон, планшет,
ноутбук, настольный компьютер). Язык интерфейса~--- русский.

\tzsubsec{4.3}{Требования к функциям, выполняемым системой}{tz:s4-3}
Функциональные требования сгруппированы по подсистемам и описаны в соответствии со
спецификацией требований к программному обеспечению (SRS) по методике К.~Вигерса.
Каждому требованию присвоен идентификатор вида ФТ-N и приоритет (высокий, средний или
низкий).

\tzsubsubsec{4.3.1}{Аутентификация и управление сессией}
Подсистема обеспечивает регистрацию пользователей и разграничение доступа к данным.
\begin{compactlist}
  \item ФТ-1 (высокий). Система должна обеспечивать регистрацию пользователя по адресу электронной почты и паролю.
  \item ФТ-2 (высокий). Система должна выполнять аутентификацию пользователя и выдавать токен доступа и токен обновления.
  \item ФТ-3 (средний). Система должна автоматически обновлять токен доступа без повторного ввода учетных данных.
  \item ФТ-4 (высокий). Система должна предоставлять каждому пользователю доступ только к его собственным задачам и маршрутам.
\end{compactlist}

\tzsubsubsec{4.3.2}{Управление задачами}
\begin{compactlist}
  \item ФТ-5 (высокий). Система должна обеспечивать создание, редактирование и удаление задачи с указанием названия, адреса, длительности выполнения и временного окна.
  \item ФТ-6 (средний). Система должна обеспечивать клонирование существующей задачи.
  \item ФТ-7 (средний). Система должна поддерживать изменение порядка задач в списке.
  \item ФТ-8 (средний). Система должна обеспечивать импорт перечня задач из файлов форматов CSV и XLSX.
  \item ФТ-9 (средний). Система должна обеспечивать экспорт перечня задач в форматы CSV и XLSX.
\end{compactlist}

\tzsubsubsec{4.3.3}{Геокодирование и построение матрицы расстояний}
\begin{compactlist}
  \item ФТ-10 (высокий). Система должна выполнять геокодирование адресов задач через внешний картографический сервис.
  \item ФТ-11 (высокий). Система должна строить матрицу расстояний и времени перемещения между адресами задач.
  \item ФТ-12 (средний). Система должна поддерживать выбор способа перемещения: автомобиль, пешеход, общественный транспорт.
  \item ФТ-13 (средний). Система должна кэшировать результаты геокодирования и расчета расстояний.
\end{compactlist}

\tzsubsubsec{4.3.4}{Оптимизация маршрута}
\begin{compactlist}
  \item ФТ-14 (высокий). Система должна вычислять оптимальную последовательность выполнения задач с учетом временных окон и длительности выполнения.
  \item ФТ-15 (средний). Система должна поддерживать фиксацию начальной и конечной точек маршрута.
  \item ФТ-16 (средний). Система должна поддерживать попарные ограничения порядка посещения задач.
  \item ФТ-17 (высокий). Система должна рассчитывать для каждой остановки время прибытия, ожидания, начала и завершения обслуживания.
\end{compactlist}

\tzsubsubsec{4.3.5}{Визуализация и контроль}
\begin{compactlist}
  \item ФТ-18 (высокий). Система должна отображать построенный маршрут на карте с пронумерованными точками.
  \item ФТ-19 (средний). Система должна обнаруживать и отмечать конфликты временных окон.
  \item ФТ-20 (низкий). Система должна отображать сводные показатели маршрута: суммарное расстояние, время в пути, обслуживания и ожидания.
\end{compactlist}

\tzsubsec{4.4}{Требования к видам обеспечения}{tz:s4-4}

\tzsubsubsec{4.4.1}{Требования к информационному обеспечению}
Хранение данных должно осуществляться под управлением реляционной системы управления
базами данных (PostgreSQL~16). Структура базы данных управляется механизмом миграций.
Данные, вводимые пользователем (адреса, временные окна, загружаемые файлы), должны
проходить валидацию формата и содержания.

\tzsubsubsec{4.4.2}{Требования к лингвистическому обеспечению}
Язык пользовательского интерфейса~--- русский. Исходный код и сопроводительная
документация ведутся с использованием русского и английского языков.

\tzsubsubsec{4.4.3}{Требования к программному обеспечению}
В состав программных средств входят следующие технологии:
\begin{tzdash}
  \item основной язык разработки серверной части~--- Go 1.23;
  \item веб-фреймворк серверной части~--- Gin;
  \item система управления базами данных~--- PostgreSQL 16;
  \item основной язык разработки клиентской части~--- TypeScript;
  \item библиотека построения интерфейса~--- React 18;
  \item сборщик клиентского приложения~--- Vite 6;
  \item картографический сервис~--- Yandex Maps JavaScript API;
  \item резервный сервис маршрутизации~--- OSRM;
  \item система контейнеризации~--- Docker и Docker Compose;
  \item система контроля версий~--- Git.
\end{tzdash}

\tzsubsubsec{4.4.4}{Требования к техническому обеспечению}
Требования к техническим характеристикам сервера: процессор с тактовой частотой не ниже
1~ГГц, оперативная память не менее 512~МБ, дисковое пространство не менее 1~ГБ,
подключение к сети Интернет.

Требования к устройству пользователя: устройство с веб-браузером, поддерживающим
JavaScript ES2020 (Google Chrome 90 и выше, Mozilla Firefox 88 и выше, Safari 14 и выше,
Microsoft Edge 90 и выше, Yandex Browser 25 и выше), подключение к сети Интернет.

\tzsubsubsec{4.4.5}{Требования к методическому обеспечению}
Методическое обеспечение системы включает следующую документацию: руководство по
развертыванию (файл README), документацию исходного кода (комментарии формата godoc для
серверной части и TSDoc для клиентской части).

\tzsubsec{4.5}{Требования к численности и квалификации сотрудников}{tz:s4-5}
Для эксплуатации системы определены роли:
\begin{tzdash}
  \item системный администратор~--- обеспечивает развертывание и сопровождение серверной части; должен владеть основами администрирования операционных систем семейства Linux, контейнеризации Docker и резервного копирования баз данных;
  \item пользователь~--- конечный пользователь веб-приложения; специальная подготовка не требуется, достаточно базовых навыков работы с веб-браузером.
\end{tzdash}

\tzsubsec{4.6}{Требования к эргономике и технической эстетике}{tz:s4-6}
Взаимодействие пользователя с системой осуществляется через графический интерфейс.
Интерфейс должен быть понятным и удобным, не перегруженным графическими элементами,
обеспечивать быстрое отображение экранных форм и удобный доступ к основным функциям.
Управление осуществляется с помощью указывающего устройства (<<мышь>>) или сенсорного
экрана; клавиатурный ввод используется при заполнении текстовых и числовых полей. При
вводе недопустимых данных система должна выдавать пользователю поясняющее сообщение и
возвращаться в рабочее состояние.

Система подвергается модульному тестированию серверной и клиентской частей, а также

разделе~1 настоящего технического задания. Все программные изделия передаются Заказчику
в виде готовых модулей и исходного кода.

\tzsubsec{7.3}{Статус приемочной комиссии}{tz:s7-3}
Итоговая приемка осуществляется в форме защиты выпускной квалификационной работы перед
государственной экзаменационной комиссией: демонстрация работы системы на типовом
сценарии, проверка выполнения функциональных и нефункциональных требований, проверка
результатов нагрузочного тестирования.

% ====================== 8 ПОДГОТОВКА ОБЪЕКТА ============================
\tzsec{8}{Требования к подготовке объекта автоматизации к вводу системы в действие}{tz:s8}
Для ввода системы в действие необходимо:
\begin{compactlist}
  \item обеспечить сервер с установленными Docker Engine и Docker Compose;
  \item получить ключ доступа к Yandex Maps JavaScript API;
  \item установить секретный ключ для подписи токенов JWT длиной не менее 32~символов;
  \item сконфигурировать список допустимых источников запросов (CORS);
  \item обеспечить резервное копирование данных системы управления базами данных штатными средствами.
\end{compactlist}
