\section{Исходное состояние объекта и характеристика предметной области}

При наличии у задач временных окон (например, «с 9:00 до 12:00»)
пользователь вынужден вручную сопоставлять время перемещения, длительность
выполнения и интервалы доступности каждой точки~\cite{alessandretti2022urban,posledynyaya_milya},
а с ростом числа задач трудоемкость такого планирования и вероятность ошибок
быстро увеличиваются~\cite{reshenie_zadach_planirovaniya2020}.

Целевой аудиторией системы являются:

\begin{compactlist}
  \item частные пользователи, планирующие личные дела в городе;
  \item мастера и специалисты на выезде;
  \item курьеры малого бизнеса;
  \item индивидуальные предприниматели;
  \item диспетчеры, формирующие небольшие маршруты вручную.
\end{compactlist}

Особенностью данной предметной области является необходимость одновременного учета:
\begin{compactlist}
  \item географического расположения объектов;
  \item временных ограничений;
  \item длительности выполнения задач;
  \item минимизации времени перемещения и ожидания.
\end{compactlist}

\section{Постановка проблемы и формирование цели разработки}

Анализ исходного состояния показал, что основной проблемой является отсутствие доступного инструмента, объединяющего управление задачами и автоматическую маршрутизацию с учетом временных окон.

Ручной подход:

\begin{compactlist}
  \item требует значительных временных затрат;
  \item не гарантирует оптимальность маршрута;
  \item становится неэффективным при увеличении числа точек;
  \item не обеспечивает формализованного учета временных ограничений.
\end{compactlist}

Целью разработки является создание веб-приложения, обеспечивающего
автоматизированное формирование оптимального маршрута выполнения задач
с учетом их географического положения, временных окон и длительности выполнения.

На основании цели сформирован следующий перечень функций:

\begin{compactlist}
  \item создание, редактирование, удаление и клонирование задач;
  \item импорт задач из файлов формата CSV и XLSX (Excel);
  \item экспорт задач в форматах CSV и XLSX (Excel);
  \item получение матрицы расстояний через внешние API;
  \item вычисление оптимальной последовательности выполнения задач;
  \item поддержка дополнительных ограничений маршрута: фиксация начальной и конечной точки, задание порядка выполнения пар задач;
  \item выбор способа передвижения (автомобиль, пешком, общественный транспорт);
  \item расчет времени прибытия, ожидания и завершения для каждой остановки;
  \item визуальное обнаружение конфликтов временных окон;
  \item визуализация маршрута на карте.
\end{compactlist}

Для обеспечения соответствия назначению определены следующие нефункциональные требования:

\begin{compactlist}
  \item время ответа сервера — не более 2 секунд при типовой нагрузке 5 запросов в секунду;
  \item поддержка современных браузеров (Google Chrome версии 148 и выше, Yandex Browser версии 25 и выше);
  \item масштабируемость до 100 одновременных пользователей;
  \item устойчивость к повторным запросам внешних API за счет кэширования.
\end{compactlist}

\section{Обоснование выбора технологий и платформ}

На основании сформированных функциональных и нефункциональных требований
произведено обоснование выбора серверной и клиентской платформ, системы
управления базами данных и внешнего картографического сервиса.
Ниже последовательно рассмотрены принятые решения по каждому из перечисленных компонентов
и сводный технологический стек системы.

Выбор серверной платформы. В качестве языка для серверной части выбран Go~\cite{golang}
со следующими характеристиками, существенными для разрабатываемого приложения:

\begin{compactlist}
  \item статическая типизация, снижающая риск ошибок на этапе компиляции;
  \item встроенная модель конкурентности на основе горутин~\cite{saioc2023goroutine},
        обеспечивающая обслуживание большого числа одновременных HTTP-соединений
        без выделения отдельного потока операционной системы на каждый запрос;
  \item компиляция в нативный исполняемый файл, что дает малый объем образа
        контейнера и предсказуемое потребление ресурсов.
\end{compactlist}

Выбор системы управления базами данных. В качестве СУБД выбрана PostgreSQL~\cite{PostgreSQL}.
Обоснование:

\begin{compactlist}
  \item типизированные временные типы (\texttt{TIMESTAMPTZ}, \texttt{DATE},
        \texttt{TIME}), удобные для хранения временных окон задач;
  \item непрерывное промышленное применение с 1996~года, стабильный
        релизный цикл и соответствие стандарту SQL:2016~\cite{PostgreSQL};
  \item открытая лицензия и отсутствие лицензионных платежей при коммерческой
        эксплуатации.
\end{compactlist}

Выбор клиентских технологий. Для реализации пользовательского интерфейса выбран язык TypeScript~\cite{cherny2020ts}
с библиотекой React~\cite{banks2018react}. Причины выбора:

\begin{compactlist}
  \item компонентный подход, позволяющий повторно использовать

  \item развитая экосистема готовых компонентов и картографических библиотек;
  \item статическая типизация TypeScript, повышающая качество и
        понятность кода по сравнению с JavaScript~\cite{bogner2022ts}.
\end{compactlist}

\section{Анализ алгоритмических подходов к задаче маршрутизации с временными окнами}

Решаемая задача относится к классу <<задача коммивояжера с временными окнами>>
(Travelling Salesman Problem with Time Windows, TSPTW)~--- обобщению
классической задачи коммивояжера~\cite{held1962dp}, в котором каждой вершине
маршрута сопоставлен допустимый интервал начала обслуживания.
Пользователь задает перечень адресов с временными окнами и длительностью обслуживания,
а система должна построить порядок посещения, минимизирующий суммарное время маршрута
с учетом ожиданий перед открытием окон. Прибытие в вершину раньше открытия окна
влечет ожидание; прибытие после закрытия окна делает обслуживание невозможным.
Поскольку при отсутствии временных ограничений TSPTW сводится к классической задаче коммивояжера,
она наследует его NP-трудность~\cite{cormen2013algorithms,ahonenuk2010algos} и в общем случае
не имеет известного полиномиального точного алгоритма решения. Систематический обзор практических подходов к решению NP-трудных комбинаторных задач приведен в~\cite{skiena2018algorithm,sedgewick2014algorithms}.

Формализуем задачу. Пусть задан граф $G = (V, E)$, где $V = \{v_0, v_1, \ldots, v_n\}$ --- множество
узлов (задач пользователя), $E$ --- множество дуг с матрицей расстояний $d_{ij}$
и матрицей времен перемещения $t_{ij}$.

Каждый узел $v_i$ ($i \geq 1$) характеризуется:
\begin{compactlist}
  \item временным окном $[a_i,\, b_i]$~--- допустимым интервалом начала обслуживания;
  \item длительностью обслуживания $s_i$ (минуты).
\end{compactlist}

Если маршрутный агент прибывает в узел $v_i$ в момент $\tau_i < a_i$, он ожидает
до момента $a_i$; если $\tau_i > b_i - s_i$~--- обслуживание начать невозможно
(нарушение ограничения).

Цель: найти порядок посещения всех узлов, минимизирующий суммарное время
маршрута $T = \sum_{i} t_{ij} + \sum_{i} w_i$, где $w_i = \max(0,\; a_i - \tau_i)$~---
время ожидания в узле $v_i$, при соблюдении условий $\tau_i \leq b_i - s_i$ для всех $i$.

На рисунке~\ref{fig:vrptw_illustration} приведен пример графа задачи TSPTW
с тремя узлами. Ребра графа подписаны временем перемещения $d_{ij}$ (в минутах),
получаемым из матрицы расстояний внешнего API. Алгоритм NNH-TW выбирает
оптимальный порядок посещения: $v_0 \to v_2 \to v_1$~--- посещение ближайшей
допустимой точки на каждом шаге.

Обоснование выбора алгоритма. Для разрабатываемого веб-приложения, ориентированного на частных пользователей
и малый бизнес, был выбран алгоритм <<ближайшего соседа с временными окнами>>
(NNH-TW, Nearest Neighbour Heuristic with Time Windows) по следующим причинам:

\begin{compactlist}
  \item Полиномиальная сложность $O(n^3)$: на каждом из $n$~шагов
        основного цикла для каждого из $n$~кандидатов выполняется
        одношаговый просмотр вперед по $n$~оставшимся узлам.
        Как показано в таблице~\ref{tab:algo_perf}, среднее время работы
        при $n = 30$ составляет несколько микросекунд --- на три-четыре
        порядка меньше задержки получения матрицы расстояний от внешнего API;
  \item Предсказуемость: время работы зависит от числа задач,
        что гарантирует выполнение нефункционального требования по времени ответа;
  \item Качество решений: жадные конструктивные эвристики
        обеспечивают приемлемое качество решений при низких вычислительных
        затратах~\cite{avdoshin2018heuristics}, что достаточно для целей
        планирования личных задач и курьерских маршрутов малого масштаба.
\end{compactlist}

\section{Обзор аналогов и сравнительный анализ}

Существующие программные решения, частично пересекающиеся с задачами
разрабатываемой системы, можно разделить на три класса.

Первый класс~--- приложения для управления задачами
(Todoist~\cite{todoist}, Microsoft To~Do~\cite{ms_todo}):
реализуют полноценное создание, редактирование и удаление задач,
поддерживают напоминания и многоплатформенную синхронизацию,
однако полностью лишены функций геокодирования адресов и построения маршрутов.

Второй класс~--- навигационные сервисы
(Google Maps~\cite{google_maps}, Yandex карты~\cite{yandex_maps}, 2GIS~\cite{2gis}):
обеспечивают прокладку маршрутов по нескольким точкам,
однако не поддерживают автоматическую оптимизацию порядка посещения
и не предоставляют средств управления задачами~\cite{google_maps_help}.

Третий класс~--- специализированные логистические платформы
(Routific~\cite{routific}, Relog~\cite{relog},
Яндекс Маршрутизация~\cite{yandex_routing}, Spoke~\cite{spoke}):
сочетают геокодирование, оптимизацию маршрутов и учет временных окон,
однако ориентированы на корпоративное управление автопарком
(массовая обработка заказов, несколько водителей, диспетчеры)
и недоступны для индивидуального применения без коммерческой подписки.

\section{Выводы}

В первой главе проведен анализ предметной области, выявлены ограничения
существующих инструментов и обоснована актуальность разработки системы
планирования маршрутов с временными окнами. Сформулированы цель и назначение

Сравнительный анализ алгоритмических подходов к задаче TSPTW (полный перебор,
динамическое программирование, жадные эвристики, метаэвристики) показал, что для
целевого масштаба системы ($n < 50$) и требования по времени ответа наиболее
подходящим является алгоритм ближайшего соседа с временными окнами (NNH-TW)
с полиномиальной сложностью $O(n^3)$.

На основании сравнения технологий выбран стек разработки: Go, PostgreSQL,
React/TypeScript, Vite, Яндекс JS API, Docker Compose. Анализ аналогов
подтвердил целесообразность создания решения, ориентированного на частных
пользователей и малый бизнес.
