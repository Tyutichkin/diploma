\section{Исходное состояние объекта и характеристика предметной области}

В настоящее время большинство пользователей решают задачу планирования
маршрута вручную. Типичный сценарий включает формирование списка дел в
менеджере задач, последующий поиск адресов в навигационном сервисе и
самостоятельное определение порядка посещения точек. При наличии временных
окон (например, «с 9:00 до 12:00») пользователь вынужден дополнительно сопоставлять время перемещения и длительность выполнения задачи.

Существующие цифровые инструменты можно разделить на две группы:
\begin{itemize}
  \item менеджеры задач (не учитывают пространственный фактор);
  \item навигационные сервисы (не работают с временными окнами и списками задач).
\end{itemize}

Таким образом, пользователь вынужден использовать несколько инструментов одновременно,
что увеличивает трудозатраты и повышает вероятность ошибок \cite{reshenie_zadach_planirovaniya2020}.

Целевой аудиторией системы являются:

\begin{itemize}
  \item частные пользователи, планирующие личные дела в городе;
  \item мастера и специалисты на выезде;
  \item курьеры малого бизнеса;
  \item индивидуальные предприниматели;
  \item диспетчеры, формирующие небольшие маршруты вручную.
\end{itemize}

Особенностью данной предметной области является необходимость одновременного учета:
\begin{itemize}
  \item географического расположения объектов;
  \item временных ограничений;
  \item длительности выполнения задач;
  \item минимизации времени перемещения и ожидания.
\end{itemize}

Таким образом, предметная область представляет собой систему с признаками логистической оптимизации, однако в упрощенном масштабе, ориентированном на одного пользователя или малый бизнес \cite{alessandretti2022urban}.

\section{Постановка проблемы и формирование цели разработки}

Анализ исходного состояния показал, что основной проблемой является отсутствие доступного инструмента, объединяющего управление задачами и автоматическую маршрутизацию с учетом временных окон.

Ручной подход:

\begin{itemize}
  \item требует значительных временных затрат;
  \item не гарантирует оптимальность маршрута;
  \item становится неэффективным при увеличении числа точек;
  \item не обеспечивает формализованного учета временных ограничений.
\end{itemize}

Задача рационального планирования маршрута с учётом временных ограничений
относится к классу задач маршрутизации с временными окнами
(Vehicle Routing Problem with Time Windows, VRPTW) ---
известной NP-трудной задаче комбинаторной оптимизации \cite{hertrich2019sweep, reshenie_zadach_marshrutizasii2022, iklassov2024svrptw}.

Целью разработки является создание веб-приложения, обеспечивающего
автоматизированное формирование оптимального маршрута выполнения задач
с учетом их географического положения, временных окон и длительности выполнения.

Назначение продукта заключается в цифровой трансформации процесса ручного планирования
маршрута в автоматизированный процесс.

На основании цели сформирован следующий перечень функций:

\begin{itemize}
  \item создание, редактирование и удаление задач;
  \item хранение географических координат;
  \item получение матрицы расстояний через внешние API;
  \item вычисление оптимальной последовательности выполнения задач;
  \item расчет времени прибытия, ожидания и завершения;
  \item визуализация маршрута на карте;
  \item экспорт маршрута в формате JSON.
\end{itemize}

Для обеспечения соответствия назначению определены следующие нефункциональные требования:

\begin{itemize}
  \item время ответа сервера — не более 2 секунд при типовой нагрузке;
  \item поддержка современных браузеров;
  \item масштабируемость до 100 одновременных пользователей;
  \item устойчивость к повторным запросам внешних API за счет кэширования.
\end{itemize}

\section{Обоснование выбора технологий и платформ}

\subsection{Выбор серверной платформы}

В качестве языка для написания серверной части был выбран Golang\cite{golang}.

Выбор языка Golang\cite{golang} обусловлен:

\begin{itemize}
  \item статической типизацией, снижающей риск ошибок;
  \item встроенной моделью конкурентности \cite{kalwarowskyj2023golang};
  \item наличием практического опыта разработки.
\end{itemize}

\subsection{Выбор СУБД и работы с геоданными}

В качестве СУБД выбрана PostgreSQL\cite{PostgreSQL}.

Обоснование выбора:

\begin{itemize}
  \item наличие геометрических индексов (GiST\cite{PostgreSQL_gist});
  \item высокая надежность и зрелость платформы;
  \item наличием практического опыта разработки.
\end{itemize}

Причины выбора:

\section{Анализ алгоритмических подходов к задаче маршрутизации с временными окнами}

Задача, решаемая в данной работе, относится к классу VRPTW, рассмотренному в предыдущем разделе, ---
обобщению классической задачи коммивояжёра (TSP) с дополнительными временными ограничениями.

\subsection{Формальная постановка задачи}

Пусть задан граф $G = (V, E)$, где $V = \{v_0, v_1, \ldots, v_n\}$ --- множество
узлов (задач пользователя), $E$ --- множество дуг с матрицей расстояний $d_{ij}$
и матрицей времён перемещения $t_{ij}$.

Каждый узел $v_i$ ($i \geq 1$) характеризуется:
\begin{itemize}
  \item временны́м окном $[a_i,\, b_i]$~--- допустимым интервалом начала обслуживания;
  \item длительностью обслуживания $s_i$ (минуты).
\end{itemize}

Если маршрутный агент прибывает в узел $v_i$ в момент $\tau_i < a_i$, он ожидает
до момента $a_i$; если $\tau_i > b_i - s_i$~--- обслуживание начать невозможно
(нарушение ограничения).

\textbf{Цель:} найти порядок посещения всех узлов, минимизирующий суммарное время
маршрута $T = \sum_{i} t_{ij} + \sum_{i} w_i$, где $w_i = \max(0,\; a_i - \tau_i)$~---
время ожидания в узле $v_i$, при соблюдении условий $\tau_i \leq b_i - s_i$ для всех $i$.

  \label{tab:algorithms_compare}
  \begin{tabular}{|p{3.5cm}|p{2.2cm}|p{2.2cm}|p{5.5cm}|}

$\mathit{pop}$~--- размер популяции.

\subsection{Обоснование выбора эвристики NNH-TW}

Для разрабатываемого веб-приложения, ориентированного на частных пользователей
и малый бизнес, был выбран алгоритм <<ближайшего соседа с временными окнами>>
(NNH-TW, Nearest Neighbour Heuristic with Time Windows) по следующим причинам:

\begin{itemize}
  \item \textbf{Квадратичная сложность} $O(n^2)$ обеспечивает мгновенное
        время ответа: при $n = 30$ задачах алгоритм выполняется менее чем за 1~мс
        на серверном оборудовании;
  \item \textbf{Предсказуемость}: время работы линейно зависит от числа задач,
        что гарантирует выполнение нефункционального требования по времени ответа
        (не более 2~секунд);
  \item \textbf{Качество решений}: при $n < 30$ узлов жадная эвристика
        даёт результат, не превышающий оптимум более чем на 15--25\%
        \cite{hertrich2019sweep}, что приемлемо для целей планирования
        личных задач и курьерских маршрутов малого масштаба;
  \item \textbf{Расширяемость}: реализованный интерфейс \texttt{Optimizer}
        позволяет заменить алгоритм на более мощный (например, ACO или GA)
        без изменения остального кода системы.
\end{itemize}

\section{Выводы}

Проведён анализ предметной области, выявлены ограничения существующих инструментов
и обоснована актуальность разработки системы планирования маршрутов с учётом
временных окон. Сформулирована цель и назначение продукта, определён перечень
функций и нефункциональных требований.

Проведён сравнительный анализ алгоритмических подходов к задаче VRPTW:
полный перебор, динамическое программирование, жадные эвристики и метаэвристики.
Обоснован выбор алгоритма NNH-TW с квадратичной сложностью $O(n^2)$ как наиболее
подходящего для целевого масштаба системы ($n < 50$) и требований по времени ответа.

На основании сравнительного анализа технологий выбран стек разработки,
обеспечивающий требуемую производительность и масштабируемость системы.
Проведённый анализ аналогов подтвердил целесообразность создания специализированного
решения, ориентированного на частных пользователей и малый бизнес.
