\section{Исходное состояние объекта и характеристика предметной области}

При наличии у задач временных окон (например, «с 9:00 до 12:00»)
пользователь вынужден вручную сопоставлять время перемещения, длительность
выполнения и интервалы доступности каждой точки~\cite{alessandretti2022urban,posledynyaya_milya},
что многократно повышает трудоемкость планирования с ростом числа задач.

Существующие цифровые инструменты можно разделить на две группы:
\begin{itemize}
  \item приложения для управления задачами (не учитывают пространственный фактор);
  \item навигационные сервисы (не работают с временными окнами и списками задач).
\end{itemize}

Таким образом, пользователь вынужден использовать несколько инструментов одновременно,
что увеличивает трудозатраты и повышает вероятность ошибок \cite{reshenie_zadach_planirovaniya2020}.

Целевой аудиторией системы являются:

\begin{itemize}
  \item частные пользователи, планирующие личные дела в городе;
  \item мастера и специалисты на выезде;
  \item курьеры малого бизнеса;
  \item индивидуальные предприниматели;
  \item диспетчеры, формирующие небольшие маршруты вручную.
\end{itemize}

Особенностью данной предметной области является необходимость одновременного учета:
\begin{itemize}
  \item географического расположения объектов;
  \item временных ограничений;
  \item длительности выполнения задач;
  \item минимизации времени перемещения и ожидания.
\end{itemize}

\section{Постановка проблемы и формирование цели разработки}

Анализ исходного состояния показал, что основной проблемой является отсутствие доступного инструмента, объединяющего управление задачами и автоматическую маршрутизацию с учетом временных окон.

Ручной подход:

\begin{itemize}
  \item требует значительных временных затрат;
  \item не гарантирует оптимальность маршрута;
  \item становится неэффективным при увеличении числа точек;
  \item не обеспечивает формализованного учета временных ограничений.
\end{itemize}

Задача рационального планирования маршрута одного исполнителя с учетом
временных ограничений относится к классу задач коммивояжёра
с временными окнами (Travelling Salesman Problem with Time Windows, TSPTW) ---
частному случаю более общей задачи маршрутизации транспортных средств
с временными окнами (Vehicle Routing Problem with Time Windows, VRPTW),
сводящемуся к одному агенту без ограничений по вместимости.
Классическая постановка VRPTW и систематическое сравнение
эвристических алгоритмов для ее решения впервые приведены в
работе~\cite{solomon1987vrptw}.
Обе задачи являются NP-трудными задачами комбинаторной оптимизации
\cite{hertrich2019sweep, reshenie_zadach_marshrutizasii2022, iklassov2024svrptw, obzor_dvrptw}.

Целью разработки является создание веб-приложения, обеспечивающего
автоматизированное формирование оптимального маршрута выполнения задач
с учетом их географического положения, временных окон и длительности выполнения.

На основании цели сформирован следующий перечень функций:

\begin{itemize}
  \item создание, редактирование, удаление и клонирование задач;
  \item отметка задачи как выполненной;
  \item импорт задач из файлов CSV и Excel (XLSX);
  \item хранение географических координат с автодополнением адресов;
  \item получение матрицы расстояний через внешние API;
  \item вычисление оптимальной последовательности выполнения задач;
  \item поддержка дополнительных ограничений маршрута: фиксация начальной и конечной точки, задание порядка выполнения пар задач;
  \item выбор режима транспорта (автомобиль, пешком, общественный транспорт);
  \item расчет времени прибытия, ожидания и завершения для каждой остановки;
  \item визуальное обнаружение конфликтов временных окон;
  \item визуализация маршрута на карте с детализацией по сегментам;
  \item экспорт задач в форматах CSV и Excel (XLSX).
\end{itemize}

Для обеспечения соответствия назначению определены следующие нефункциональные требования:

\begin{itemize}
  \item время ответа сервера — не более 2 секунд при типовой нагрузке;
  \item поддержка современных браузеров;
  \item масштабируемость до 100 одновременных пользователей;
  \item устойчивость к повторным запросам внешних API за счет кэширования.
\end{itemize}

\subsection{Выбор серверной платформы}

В качестве языка для написания серверной части был выбран Golang\cite{golang}.

Выбор языка Golang\cite{golang} обусловлен:

\begin{itemize}

  \item встроенной моделью конкурентности на основе горутин \cite{saioc2023goroutine};
  \item наличием практического опыта разработки.
\end{itemize}

\subsection{Выбор СУБД и работы с геоданными}

В качестве СУБД выбрана PostgreSQL\cite{PostgreSQL}.

Обоснование выбора:

\begin{itemize}
  \item наличие геометрических индексов (GiST\cite{PostgreSQL_gist});
  \item непрерывное промышленное применение с 1996~года; стабильный релизный цикл и соответствие стандарту SQL:2016~\cite{PostgreSQL};
  \item наличием практического опыта разработки.
\end{itemize}

\subsection{Выбор клиентских технологий}

Для реализации пользовательского интерфейса был выбран React\cite{react}.

Причины выбора:

\begin{itemize}
  \item компонентный подход к разработке;
  \item развитая экосистема;
  \item наличие поддержки картографических библиотек.
\end{itemize}

В проекте применяется TypeScript --- статически типизированное надмножество JavaScript,
что обеспечивает раннее обнаружение ошибок на этапе компиляции.
Эмпирическое исследование 604~проектов на GitHub подтверждает, что TypeScript-проекты
демонстрируют значительно более высокое качество и понятность кода
по сравнению с аналогами на JavaScript~\cite{bogner2022ts}.

\section{Анализ алгоритмических подходов к задаче маршрутизации с временными окнами}

Задача, решаемая в данной работе, относится к классу TSPTW, рассмотренному в предыдущем разделе, ---
обобщению классической задачи коммивояжера (TSP)~\cite{held1962dp} с дополнительными временными ограничениями.

\subsection{Формальная постановка задачи}

Пусть задан граф $G = (V, E)$, где $V = \{v_0, v_1, \ldots, v_n\}$ --- множество
узлов (задач пользователя), $E$ --- множество дуг с матрицей расстояний $d_{ij}$
и матрицей времен перемещения $t_{ij}$.

Каждый узел $v_i$ ($i \geq 1$) характеризуется:
\begin{itemize}
  \item временным окном $[a_i,\, b_i]$~--- допустимым интервалом начала обслуживания;
  \item длительностью обслуживания $s_i$ (минуты).
\end{itemize}

Если маршрутный агент прибывает в узел $v_i$ в момент $\tau_i < a_i$, он ожидает
до момента $a_i$; если $\tau_i > b_i - s_i$~--- обслуживание начать невозможно
(нарушение ограничения).

\textbf{Цель:} найти порядок посещения всех узлов, минимизирующий суммарное время
маршрута $T = \sum_{i} t_{ij} + \sum_{i} w_i$, где $w_i = \max(0,\; a_i - \tau_i)$~---
время ожидания в узле $v_i$, при соблюдении условий $\tau_i \leq b_i - s_i$ для всех $i$.

На рисунке~\ref{fig:vrptw_illustration} приведен пример графа задачи TSPTW
с тремя узлами. Ребра графа подписаны временем перемещения $d_{ij}$ (в минутах),
получаемым из матрицы расстояний внешнего API. Алгоритм NNH-TW выбирает
оптимальный порядок посещения: $v_0 \to v_2 \to v_1$~--- посещение ближайшей
допустимой точки на каждом шаге.

\subsection{Обоснование выбора эвристики NNH-TW}

Для разрабатываемого веб-приложения, ориентированного на частных пользователей
и малый бизнес, был выбран алгоритм <<ближайшего соседа с временными окнами>>
(NNH-TW, Nearest Neighbour Heuristic with Time Windows) по следующим причинам:

\begin{itemize}
  \item \textbf{Полиномиальная сложность} $O(n^3)$: на каждом из $n$~шагов
        основного цикла для каждого из $n$~кандидатов выполняется
        одношаговый просмотр вперед (look-ahead) по $n$~оставшимся узлам.
        Экспериментально (см.~таблицу~\ref{tab:algo_perf} в разделе
        <<Производительность алгоритма оптимизации>>) среднее время работы
        при $n = 30$ составляет несколько микросекунд --- на три-четыре
        порядка меньше задержки получения матрицы расстояний от внешнего API;
  \item \textbf{Предсказуемость}: время работы линейно зависит от числа задач,
        что гарантирует выполнение нефункционального требования по времени ответа
        (не более 2~секунд);
  \item \textbf{Качество решений}: жадные конструктивные эвристики
        обеспечивают приемлемое качество решений при низких вычислительных
        затратах~\cite{avdoshin2018heuristics}, что достаточно для целей
        планирования личных задач и курьерских маршрутов малого масштаба;
  \item \textbf{Расширяемость}: реализованный интерфейс \texttt{Optimizer}
        позволяет заменить алгоритм на более мощный (например, ACO или GA)
        без изменения остального кода системы.
\end{itemize}

\section{Обзор аналогов и сравнительный анализ}

Существующие программные решения, частично пересекающиеся с задачами
разрабатываемой системы, можно разделить на три класса.

\textbf{Первый класс~--- приложения для управления задачами}
(Todoist~\cite{todoist}, Microsoft To~Do~\cite{ms_todo}):
реализуют полноценное создание, редактирование и удаление задач,
поддерживают напоминания и многоплатформенную синхронизацию,
однако полностью лишены функций геокодирования адресов и построения маршрутов.

\textbf{Второй класс~--- навигационные сервисы}
(Google Maps~\cite{google_maps}):
обеспечивают прокладку маршрутов по нескольким точкам (не более 10 остановок),
однако не поддерживают автоматическую оптимизацию порядка посещения
и не предоставляют средств управления задачами~\cite{google_maps_help}.

\textbf{Третий класс~--- специализированные логистические платформы}
(Routific~\cite{routific}, Relog~\cite{relog},
Яндекс Маршрутизация~\cite{yandex_routing}, Spoke~\cite{spoke}):
сочетают геокодирование, оптимизацию маршрутов и учет временных окон,
однако ориентированы на корпоративное управление автопарком
(массовая обработка заказов, несколько водителей, диспетчеры)
и недоступны для индивидуального применения без коммерческой подписки.

не обеспечивает одновременно управление задачами, автоматическую оптимизацию

без коммерческой подписки.
Менеджеры задач первого класса лишены геолокационных функций;
навигационные сервисы второго класса не поддерживают автоматическую
оптимизацию порядка посещения и не управляют задачами;
логистические платформы третьего класса реализуют требуемый функционал,
однако ориентированы на корпоративный автопарк и недоступны
для целевой аудитории разрабатываемой системы.


\section{Выводы}

Проведен анализ предметной области, выявлены ограничения существующих инструментов
и обоснована актуальность разработки системы планирования маршрутов с учетом
временных окон. Сформулирована цель и назначение продукта, определен перечень
функций и нефункциональных требований.

Проведен сравнительный анализ алгоритмических подходов к задаче TSPTW:
полный перебор, динамическое программирование, жадные эвристики и метаэвристики.
Обоснован выбор алгоритма NNH-TW с полиномиальной сложностью $O(n^3)$ как наиболее
подходящего для целевого масштаба системы ($n < 50$) и требований по времени ответа.

На основании сравнительного анализа технологий выбран стек разработки,
обеспечивающий требуемую производительность и масштабируемость системы.
Проведенный анализ аналогов подтвердил целесообразность создания специализированного
решения, ориентированного на частных пользователей и малый бизнес.
