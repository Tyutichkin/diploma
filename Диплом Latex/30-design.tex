\subsection{Общая характеристика структуры хранения данных}

На рисунке \ref{fig:database_model} представлена логическая модель данных разрабатываемого веб-приложения.

\begin{figure}[H]
      \centering

      \caption{Модель данных}

Структура базы данных включает следующие функциональные группы сущностей:

\begin{itemize}
      \item хранение информации о пользователях;
      \item хранение задач с географической привязкой;
      \item хранение маршрутов;
      \item хранение результатов вычислений.
\end{itemize}

\subsection{Сущности, связанные с пользователями}

Сущность \texttt{users} предназначена для хранения учетных записей пользователей.
Первичный ключ \texttt{id} используется для установления связей со всеми зависимыми таблицами.
Поле \texttt{email} выполняет роль логина и имеет ограничение уникальности, что исключает дублирование учетных записей.
Пароль хранится в виде хэшированного значения, что обеспечивает безопасность аутентификации.

Сущность \texttt{refresh\_tokens} используется для поддержки механизма продления авторизации.
Каждый токен связан с конкретным пользователем через внешний ключ \texttt{user\_id}.
Хранение токена в виде хэша предотвращает его компрометацию в случае несанкционированного доступа к базе данных.

\subsection{Сущность задач}

Сущность \texttt{tasks} отражает основную предметную сущность системы — задачу, подлежащую выполнению.

Каждая запись содержит:

\begin{itemize}
      \item связь с владельцем задачи (\texttt{user\_id});
      \item текстовое описание адреса (\texttt{address\_text});
      \item географические координаты (\texttt{latitude}, \texttt{longitude}), допускающие \texttt{NULL} для задач без адреса;
      \item длительность выполнения (\texttt{duration\_min}), допускающую \texttt{NULL} для мгновенных задач;
      \item раздельные дату и время начала (\texttt{window\_start\_date}, \texttt{window\_start\_time}) и окончания (\texttt{window\_end\_date}, \texttt{window\_end\_time}) временного окна, что позволяет задавать ограничения как по дате, так и по времени;
      \item индекс сортировки (\texttt{sort\_index}) для отображения порядка в пользовательском интерфейсе;
      \item признак выполнения (\texttt{is\_completed}) для отметки завершeнных задач.
\end{itemize}

\subsection{Сущности маршрутов}

Сущность \texttt{routes} описывает факт построения маршрута для конкретного пользователя.
Она содержит сведения о статусе вычисления, источнике формирования последовательности (ручной или оптимизированный), пользовательское имя маршрута (\texttt{name}) и время создания.

Структура маршрута детализируется в сущности \texttt{route\_stops},
где каждая запись соответствует отдельной точке маршрута.
Поле \texttt{position} определяет порядок следования,
а временные поля (\texttt{arrive\_time}, \texttt{service\_start\_time}, \texttt{service\_end\_time})
позволяют зафиксировать результат работы алгоритма с учетом временных окон.

\subsection{Хранение агрегированных показателей}

Агрегированные характеристики маршрута вынесены в отдельную сущность \texttt{route\_stats}.
К таким показателям относятся суммарная длина маршрута, время перемещения, время выполнения задач и суммарное ожидание.

Выделение агрегированных данных в отдельную таблицу позволяет:
\begin{itemize}
      \item уменьшить нагрузку на основную таблицу маршрутов;
      \item обновлять статистику независимо от структуры маршрута;
      \item отделить расчетные показатели от исходных данных.
\end{itemize}

\subsection{Геометрия маршрута}

Сущность \texttt{route\_geometry} предназначена для хранения пространственного представления маршрута,
используемого при визуализации на карте.
Поле \texttt{polyline} либо \texttt{geojson\_json} содержит геометрическое описание линии маршрута,
полученное из внешнего API.

Разделение логической структуры маршрута и его геометрического представления
позволяет обновлять визуальные данные без изменения структуры остановок.

\subsection{Кэширование данных внешних API}

Результаты обращений к внешним сервисам маршрутизации
кэшируются на уровне приложения в оперативной памяти
через обёртку \texttt{CachedProvider} над интерфейсом
\texttt{distance.Provider}.
В качестве хранилища используется готовая библиотека
\texttt{hashicorp/golang-lru/v2}~\cite{golang_lru} (пакет \texttt{expirable}),
реализующая потокобезопасный LRU-кэш с ограничением размера и временем
жизни записи (TTL).
Ключом записи служит пара географических координат (округлённых до
шестого знака после запятой), что делает кэш инвариантным относительно
порядка запросов одних и тех же адресов.

Наличие кэша снижает количество обращений к внешним сервисам,
уменьшает задержки при повторной оптимизации и повышает устойчивость системы
при ограничениях со стороны API-провайдера.

\section{Архитектура системы}

\subsection{Общие принципы}

Серверная часть приложения построена по принципам чистой архитектуры
(Clean Architecture), предложенной Р.~Мартином \cite{martin2017clean}.
Ключевой принцип: зависимости направлены исключительно от внешних слоeв
(HTTP-обработчики, репозитории) к внутренним (доменные сущности и варианты использования),
но не наоборот. Это обеспечивает независимость бизнес-логики от конкретных
фреймворков, СУБД и транспортных протоколов.

\subsection{Паттерн замены алгоритма}

Ключевым архитектурным решением является интерфейс \texttt{Optimizer},
определeнный в пакете \texttt{internal/domain/route/gate/}:

\begin{itemize}
      \item метод \texttt{Optimize(ctx, graph, startTimeUnix, constraints)} принимает
            граф задач, время выезда в секундах Unix и структуру дополнительных
            ограничений (фиксированные начальная/конечная точки, попарные ограничения
            порядка посещения), возвращает порядок обхода, тайминги каждой остановки
            и агрегированную статистику;
      \item конкретная реализация \texttt{NearestNeighborTW} регистрируется
            в модуле сборки зависимостей (\texttt{internal/app/app.go});
      \item для замены алгоритма (например, на муравьиный или генетический)
            достаточно зарегистрировать новую реализацию интерфейса,
            не изменяя HTTP-обработчики, репозитории или доменные сущности.
\end{itemize}

\section{Алгоритм оптимизации маршрута}

\subsection{Описание алгоритма}

Для вычисления оптимального порядка посещения задач реализован алгоритм
«ближайшего соседа с временными окнами» (Nearest Neighbour Heuristic with
Time Windows, NNH-TW).

Алгоритм является жадной конструктивной эвристикой с одношаговым просмотром
вперeд (one-step look-ahead): на каждом шаге из допустимых кандидатов выбирается
узел с наименьшим временем завершения обслуживания, при этом предпочтение
отдаeтся <<безопасным>> кандидатам --- тем, посещение которых не делает
недостижимым ни один другой узел с временным окном. Внутри каждого класса
(безопасные / рискованные) приоритет получает кандидат с более ранним
дедлайном, что снижает вероятность пропуска срочных задач.
Алгоритм также учитывает дополнительные ограничения: фиксацию начальной
и конечной точки маршрута, а также попарные ограничения порядка посещения
(предшествование).

\subsection{Псевдокод алгоритма}

\begin{codelisting}{Псевдокод алгоритма NNH-TW с просмотром вперeд}{listing:nnh_pseudocode}
      \begin{minted}{text}
Вход: граф G(V, E), startTimeUnix, constraints{startIdx, endIdx, precedences}
Выход: порядок обхода order[], тайминги[], агрегированная статистика

1.  prereqs ← buildPrereqs(precedences)
2.  endIdx ← constraints.endIdx (или -1)
3.  Если constraints.startIdx задан:
        cur ← constraints.startIdx
    Иначе:
        cur ← узел с наиболее ранним окном среди допустимых
4.  visited[cur] ← true;  order ← [cur]
5.  currentTimeSec ← startTimeUnix + duration[cur] * 60

6.  Пока |order| < |V|:
    // Если остался только закреплённый конечный узел — ставим его
    a. Если endIdx >= 0 И все прочие посещены:
         Добавить endIdx в маршрут; выйти из цикла

    // Проход 1: допустимый узел с минимальным completionTime + look-ahead
    b. bestComp ← ∞;  bestSafe ← false;  bestDeadline ← ∞;  next ← -1
    c. Для каждого i ∉ visited, i ≠ endIdx:
         Если не выполнены предшественники i: пропустить
         arrivalSec ← currentTimeSec + travelSec[cur][i]
         Если НЕ feasible(i, arrivalSec): пропустить
         comp ← completionTime(i, arrivalSec)
         safe ← НЕ causesWindowMiss(i, comp, G, visited, endIdx)
         Если (safe > bestSafe) ИЛИ (safe = bestSafe И comp < bestComp)
              ИЛИ (safe = bestSafe И comp = bestComp И deadline[i] < bestDeadline):
             next ← i;  bestComp ← comp;  bestSafe ← safe

    // Проход 2: резервный — минимальный completionTime без учёта окна
    d. Если next = -1:
         Для каждого i ∉ visited, i ≠ endIdx:
             Если не выполнены предшественники i: пропустить
             comp ← completionTime(i, arrivalSec)
             Если comp < bestComp: next ← i

    e. waitSec ← max(0, windowStart[next] − arrivalSec)
    f. currentTimeSec ← arrivalSec + waitSec + duration[next] * 60
    g. visited[next] ← true;  order.append(next);  cur ← next

7.  Вернуть order, тайминги и статистику

feasible(i, arrivalSec):
    Если windowEnd[i] < 0: вернуть true
    Вернуть arrivalSec ≤ windowEnd[i] − duration[i] * 60

causesWindowMiss(cand, afterCandSec, G, visited, endIdx):
    Для каждого j ∉ visited, j ≠ cand, j ≠ endIdx:
        Если windowEnd[j] < 0: пропустить
        Если НЕ feasible(j, afterCandSec + travelSec[cand][j]):
            Вернуть true
    Вернуть false
  \end{minted}
\end{codelisting}

секунды~Unix):

\begin{enumerate}
      \item \textbf{Выбор стартового узла.} Узел $v_0$ имеет наиболее раннее
            окно (08:00) → $\mathrm{cur} = 0$,
            $\mathrm{currentTime} = 480 + 30 = 510$ (08:30 + 30 мин выполнения = 09:30 \textrightarrow\ мин 510).
      \item \textbf{Шаг 1. Проход~1.}
            \begin{itemize}
                  \item $v_1$: прибытие = $510 + 40 = 550$ (09:10). Окно $v_1$: 600--720 (10:00--12:00).
                        Условие: $550 \leq 720 - 20 = 700$ → допустимо. $t = 40$~мин.
                  \item $v_2$: прибытие = $510 + 15 = 525$ (08:45). Окно $v_2$: 540--600 (09:00--10:00).
                        Условие: $525 \leq 600 - 15 = 585$ → допустимо. $t = 15$~мин.
                  \item $v_2$ ближе (15 < 40) → next = 2.
            \end{itemize}
            Ожидание: $\max(0,\; 540 - 525) = 15$~мин.
            $\mathrm{currentTime} = 525 + 15 + 15 = 555$ (09:15).
      \item \textbf{Шаг 2. Проход~1.}
            \begin{itemize}
                  \item $v_1$: прибытие = $555 + 20 = 575$ (09:35).
                        Условие: $575 \leq 700$ → допустимо. next = 1.
            \end{itemize}
            Ожидание: $\max(0,\; 600 - 575) = 25$~мин.
            $\mathrm{currentTime} = 575 + 25 + 20 = 620$ (10:20).
\end{enumerate}

Итоговый порядок: $v_0 \to v_2 \to v_1$. Суммарное ожидание: $15 + 25 = 40$~мин.

\subsection{Оценка вычислительной сложности}

Алгоритм выполняет $n$ итераций основного цикла. На каждой итерации
для каждого из $n$ кандидатов выполняется одношаговый просмотр вперeд
(\texttt{causesWindowMiss}), просматривающий до $n$ оставшихся узлов.
Таким образом, сложность составляет $O(n^3)$.

При $n = 30$ задачах алгоритм выполняет порядка $30^3 = 27\,000$ элементарных
операций. Результаты бенчмаркинга, приведeнные в таблице~\ref{tab:algo_perf},
показывают, что при $n \leq 30$ время работы алгоритма составляет единицы
микросекунд, что на несколько порядков меньше задержки, вносимой получением
матрицы расстояний от внешнего API.

\subsection{Дополнительные ограничения маршрута}

Помимо временных окон, реализована поддержка трёх типов дополнительных ограничений,
задаваемых пользователем при запросе оптимизации.

\textbf{Фиксированная начальная точка.}
Если пользователь указывает идентификатор начальной задачи, алгоритм начинает обход
с соответствующего узла вместо автоматически выбранного по признаку наиболее раннего
временного окна.

\textbf{Фиксированная конечная точка.}
Если задана конечная задача, соответствующий узел исключается из стандартного процесса
выбора следующей точки.
После того как все остальные узлы посещены, конечный узел добавляется в маршрут последним.

\textbf{Ограничения порядка.}
Пользователь вправе указать пары задач вида «A до B»:
задача $A$ должна быть выполнена строго раньше задачи $B$.
При выборе следующего узла на каждом шаге алгоритм пропускает кандидатов,
для которых не все предшественники уже посещены.
Условие проверяется в обоих проходах (Pass~1 и Pass~2), что гарантирует
соблюдение ограничения независимо от наличия допустимых временных окон.

Ограничения передаются в алгоритм через структуру \texttt{Constraints} пакета
\texttt{optimizer}.
Преобразование идентификаторов задач в индексы графа выполняется на уровне
бизнес-логики (\texttt{story.Optimize}) и не затрагивает реализацию алгоритма,
что соответствует принципу единственной ответственности.

\subsection{Вывод}

Алгоритм NNH-TW при сложности $O(n^3)$ обеспечивает приемлемое качество решений~\cite{liu2023vrpheuristics}
для целевого масштаба системы ($n < 50$) и расширен поддержкой фиксированных
начальной/конечной точек и ограничений порядка выполнения.


\section{Тестирование}

\subsection{Стратегия тестирования}

В проекте реализована многоуровневая стратегия тестирования, охватывающая
как серверную, так и клиентскую части приложения.

Применяемые виды тестирования:
\begin{itemize}
      \item \textbf{Модульные тесты} --- проверка отдельных функций
            и методов в изоляции от внешних зависимостей;
      \item \textbf{Тесты с заглушками} --- тестирование вариантов
            использования (\texttt{story}) через интерфейсы с подменeнными
            реализациями репозиториев;
      \item \textbf{Тесты компонентов} --- проверка React-компонентов
            через \texttt{@testing-library/react} с симуляцией пользовательских действий;
      \item \textbf{Тесты API-клиента} --- перехват HTTP-запросов через
            Mock Service Worker (MSW) и проверка логики обновления токена.
\end{itemize}

Для написания тестов серверной части используется библиотека
\texttt{github.com/stretchr/testify}:
пакет \texttt{assert} для нестрогих проверок и
пакет \texttt{require} для немедленной остановки теста при критическом сбое.

\subsection{Тестирование алгоритма оптимизации}

Наиболее критичным компонентом с точки зрения корректности является алгоритм

\subsection{Тестирование бизнес-логики серверной части}

Варианты использования тестируются с использованием
репозиториев-заглушек, генерируемых пакетом \texttt{testify/mock}.
Такой подход позволяет тестировать бизнес-логику в изоляции от базы данных.

Покрыты следующие компоненты:
\begin{itemize}
      \item \texttt{auth/story} --- регистрация, вход, выход, обновление токена;
      \item \texttt{task/story} --- создание, редактирование, удаление задачи,
            проверка принадлежности задачи пользователю;
      \item \texttt{route/story} --- сохранение оптимизированного маршрута,
            получение маршрута по идентификатору.
\end{itemize}

\subsection{Тестирование клиентской части}

Клиентская часть тестируется с использованием стека:
\texttt{vitest}~--- тестовый раннер,
\texttt{@testing-library/react}~--- тестирование компонентов,
\texttt{msw} (Mock Service Worker)~--- перехват и подмена HTTP-запросов в тестах.

Ключевые тест-кейсы клиентской части:
\begin{itemize}
      \item Логика обновления токена: при получении ответа 401 запускается
            ровно один запрос обновления (дедупликация через общий Promise);
            после успешного обновления исходный запрос повторяется;
      \item Утилита построения матрицы расстояний: корректное формирование
            $n \times (n-1)$ запросов к мультимаршрутизатору Яндекс JS API.
\end{itemize}

\subsection{Вывод}

Реализованная стратегия тестирования охватывает все критические компоненты
системы: алгоритм оптимизации (35 тест-кейсов, включая просмотр вперeд
и ограничения), бизнес-логику серверной части
(тесты через заглушки) и клиентский API-клиент (тесты с MSW).
Использование интерфейсов и внедрение зависимостей обеспечивает возможность
полноценного тестирования бизнес-логики без обращения к реальной базе данных.

\subsection{Общая логика построения интерфейса}

На главной странице (рисунок~\ref{fig:maket_screen_main})
список задач и карта маршрута размещены в пределах одного экрана,
что позволяет немедленно оценивать влияние изменений в списке задач
на итоговый маршрут без переключения между представлениями.

\subsection{Организация рабочей области}

Рабочая область разделена на две функциональные зоны:

\begin{itemize}
      \item список задач;
      \item карта с визуализацией маршрута.
\end{itemize}

Список задач представлен в виде отдельных карточек с фиксированным набором полей,
что обеспечивает визуальное разграничение элементов при одновременном отображении нескольких задач.

Карта размещена справа, что обеспечивает постоянную визуальную связь
между порядком задач и их пространственным расположением.
Пользователь может сопоставить маршрут с реальным расположением точек
без дополнительных переходов между страницами.

\subsection{Организация ввода данных}

Добавление новой задачи реализовано через модальное окно
(рисунок \ref{fig:maket_screen_add_task}).

Поля формы сгруппированы логически: название, адрес, длительность, временное окно.
Такая последовательность соответствует естественному порядку формулирования задачи.

\subsection{Навигационная структура}

Навигация организована через верхнюю панель
(рисунок \ref{fig:maket_screen_instruction}).

В интерфейсе предусмотрены следующие разделы:

\begin{itemize}
      \item главная страница — работа с задачами и маршрутом;
      \item инструкция — описание принципа работы системы.
\end{itemize}

\subsection{Импорт и экспорт задач}

Для ускорения ввода большого количества задач реализован импорт из файлов
CSV и Excel~(XLSX). Диалог импорта отображает распознанные строки,
выделяет ошибки валидации (отсутствие названия, некорректный формат времени)
и позволяет пользователю подтвердить или отклонить каждую строку
перед сохранением. Импортированные задачи создаются пакетно через
эндпоинт \texttt{POST /api/tasks/batch}.

Экспорт задач доступен в двух форматах: CSV (библиотека \texttt{papaparse})
и Excel (библиотека \texttt{xlsx}). Экспортируются все текущие задачи
пользователя с полями: название, адрес, длительность, дата и время
временного окна.

\subsection{Поддержка пользовательского контроля}

В интерфейсе реализована возможность изменения порядка задач методом перетаскивания.

Даже при наличии автоматической оптимизации пользователь сохраняет возможность ручного управления
последовательностью выполнения.
Это обеспечивает соответствие принципу пользовательского контроля: оператор может
скорректировать автоматически сформированный порядок без повторного запуска алгоритма.

Дополнительно реализованы следующие элементы управления:
\begin{itemize}
      \item \textbf{Выбор режима транспорта:} пользователь выбирает способ перемещения
            (автомобиль, пешком, общественный транспорт), что влияет на матрицу
            расстояний и визуализацию маршрута на карте. Для режима
            <<общественный транспорт>> расчёт времени приближается авто-режимом
            из-за ограничений API мультимаршрутизации, тогда как построение и
            отображение маршрута производится корректно для всех режимов;
      \item \textbf{Фиксация начальной и конечной точки:} через контекстное меню
            карточки задачи пользователь назначает точку старта или финиша маршрута;
      \item \textbf{Ограничения порядка:} пользователь задаeт пары <<задача A
            до задачи B>>, которые алгоритм обязан соблюдать;
      \item \textbf{Обнаружение конфликтов:} интерфейс автоматически выявляет
            и подсвечивает задачи с некорректными или конфликтующими временными окнами
            как до оптимизации (взаимное перекрытие), так и после (фактическое опоздание);
      \item \textbf{Отметка выполнения:} задача может быть помечена как выполненная;
      \item \textbf{Клонирование задач:} дублирование существующей задачи для быстрого
            создания аналогичной записи.
\end{itemize}

\section{Техническая реализация}

\subsection{Состав и объeм программного кода}

Разработанное приложение состоит из двух независимых программных компонентов:
серверной части на языке Go и клиентской части на языке TypeScript с использованием
фреймворка React.

Серверная часть насчитывает 50 исходных файлов на языке Go,
организованных в соответствии с принципами чистой архитектуры.
Код распределeн по следующим функциональным пакетам:

\begin{itemize}
      \item \texttt{cmd/api} — точка входа в приложение (1 файл);
      \item \texttt{internal/config} — загрузка конфигурации из переменных окружения (1 файл);
      \item \texttt{internal/app} — сборка зависимостей (1 файл);
      \item \texttt{internal/common/ptrs} — общие вспомогательные функции (1 файл);
      \item \texttt{internal/domain} — бизнес-логика предметной области: сущности,
            интерфейсы репозиториев и варианты использования для модулей аутентификации,
            задач, маршрутов, пользователей и пакетного импорта задач (27 файлов,
            включая тесты);
      \item \texttt{internal/api/http} — HTTP-обработчики, промежуточное программное
            обеспечение, маршрутизатор и объекты передачи данных (12 файлов, включая тесты);
      \item \texttt{internal/platform/postgres} — реализации репозиториев и подключение
            к базе данных (5 файлов);
      \item \texttt{internal/platform/distance} — провайдер матрицы расстояний
            с реализацией на основе OSRM и LRU-кэшем с TTL на базе библиотеки
            \texttt{hashicorp/golang-lru/v2} (3 файла);
      \item \texttt{migrations} — SQL-миграции схемы базы данных (5 миграций, 10 файлов).
\end{itemize}

Клиентская часть содержит 77 исходных файлов TypeScript и TSX.
Из них около 30 файлов реализуют прикладную логику и компоненты страниц,
остальные относятся к библиотеке пользовательского интерфейса на основе
shadcn/ui и Radix UI. Структура клиентской части включает:

\begin{itemize}
      \item корневые компоненты приложения и конфигурация маршрутизации (3 файла);
      \item API-клиент с логикой обновления токена (2 файла);
      \item контекст аутентификации и хук \texttt{useAuth()} (1 файл);
      \item типы TypeScript для доменных сущностей (3 файла);
      \item утилиты загрузки Яндекс JS API и построения матрицы расстояний (2 файла);
      \item компоненты страниц и функциональные компоненты (11 файлов);
      \item компоненты UI-библиотеки (48 файлов).
\end{itemize}

Наиболее значимые фрагменты кода приведены в приложениях:
реализация алгоритма оптимизации маршрута — в приложении~\ref{app:lst_optimizer},
обработчики HTTP-запросов для маршрутов — в приложении~\ref{app:lst_handlers_routes},
клиент API с логикой обновления токена — в приложении~\ref{app:lst_api_client},
утилита построения матрицы расстояний — в приложении~\ref{app:lst_route_optimizer}.

\subsection{Используемые библиотеки серверной части}

В серверной части используются следующие сторонние библиотеки Go:

\begin{itemize}
      \item \texttt{github.com/gin-gonic/gin} (v1.10.0) — HTTP-фреймворк для построения
            REST API; обеспечивает маршрутизацию запросов, группировку эндпоинтов,
            обработку ошибок и привязку JSON-тела запроса к структурам данных;
      \item \texttt{github.com/gin-contrib/cors} (v1.7.2) — промежуточное программное
            обеспечение для настройки политики CORS (Cross-Origin Resource Sharing);
      \item \texttt{github.com/golang-jwt/jwt/v5} (v5.2.1) — генерация и верификация
            JSON Web Token для реализации механизма аутентификации без сохранения
            состояния на сервере;
      \item \texttt{github.com/jackc/pgx/v5} (v5.6.0) — низкоуровневый драйвер
            PostgreSQL для Go с поддержкой пула соединений; используется вместо
            стандартного \texttt{database/sql} ввиду более высокой производительности
            и поддержки специфичных типов PostgreSQL;
      \item \texttt{github.com/google/uuid} (v1.6.0) — генерация уникальных
            идентификаторов UUID версии 4 для первичных ключей всех таблиц;
      \item \texttt{golang.org/x/crypto} (v0.27.0) — функции криптографии, в частности
            \texttt{bcrypt} для хэширования паролей пользователей и токенов обновления;
      \item \texttt{github.com/stretchr/testify} (v1.9.0) — набор вспомогательных
            функций для написания тестов: утверждения \texttt{assert}/\texttt{require}
            и создание заглушек через пакет \texttt{mock}.
\end{itemize}

Для управления миграциями схемы базы данных используется инструмент
\texttt{migrate/migrate} (v4.17.1), запускаемый автоматически при старте
Docker-контейнера.

\subsection{Используемые библиотеки клиентской части}

В клиентской части задействованы следующие основные библиотеки:

\begin{itemize}
      \item \texttt{react} и \texttt{react-dom} (v18.3.1) — базовый фреймворк
            для построения компонентного пользовательского интерфейса;
      \item \texttt{react-router} (v7.13.0) — декларативная клиентская маршрутизация;
            используется для разделения приложения на страницы без перезагрузки браузера;
      \item \texttt{vite} (v6.3.5) с плагином \texttt{@vitejs/plugin-react} —
            инструмент сборки; обеспечивает быстрое обновление модулей в режиме разработки
            (HMR) и оптимизированную сборку для продакшена;
      \item \texttt{tailwindcss} (v4) — утилитарный CSS-фреймворк; используется для
            стилизации компонентов без написания отдельных файлов стилей;
      \item пакеты \texttt{@radix-ui/*} (более 20 пакетов) — безголовые примитивы
            доступного пользовательского интерфейса (диалоги, всплывающие подсказки,
            вкладки, аккордеон и др.); служат основой для компонентов shadcn/ui;
      \item \texttt{react-hook-form} (v7.55.0) — управление состоянием форм
            с минимальным количеством перерисовок; применяется в форме создания задачи;
      \item \texttt{react-dnd} и \texttt{react-dnd-html5-backend} — реализация
            перетаскивания элементов (drag-and-drop) для ручного упорядочивания задач;
      \item \texttt{sonner} (v2.0.3) — компонент всплывающих уведомлений (toast);
      \item \texttt{lucide-react} — библиотека SVG-иконок;
      \item \texttt{date-fns} — утилиты для форматирования дат и работы со временем;
      \item \texttt{papaparse} (v5.5) — парсинг и генерация файлов CSV;
            используется для импорта и экспорта задач;
      \item \texttt{xlsx} (v0.18) — чтение и запись файлов Excel (XLSX);
            используется для импорта и экспорта задач.
\end{itemize}

Для тестирования клиентской части используется стек:
\texttt{vitest} (v3.2.4) как тестовый раннер, \texttt{@testing-library/react}
для тестирования компонентов, \texttt{@testing-library/user-event} для
симуляции пользовательских действий, а также \texttt{msw} (Mock Service Worker)
для перехвата и подмены HTTP-запросов в тестах.

Картографический функционал реализован на основе
Яндекс JavaScript API и HTTP Геокодер версии~2.1~\cite{yandex_maps_js_api},
загружаемого динамически через \texttt{<script>}-тег при первом обращении к карте.
Данный API предоставляет геокодер, механизм мультимаршрутизации
для построения матрицы расстояний и инструменты визуализации
(маркеры, полилинии, управление видимой областью карты).

\subsection{Требования к техническим средствам}

Для развeртывания и эксплуатации приложения предъявляются следующие
требования к техническим средствам.

Для серверной части:

\begin{itemize}
      \item процессор: одноядерный с тактовой частотой не ниже 1~ГГц
            (рекомендуется двухъядерный и более);
      \item оперативная память: не менее 512~МБ (рекомендуется 1~ГБ и более);
      \item дисковое пространство: не менее 1~ГБ для хранения образов Docker
            и данных PostgreSQL;
      \item сетевой интерфейс: соединение с интернетом для обращения к внешним
            сервисам (Яндекс Карты, OSRM).
\end{itemize}

Для клиентской части (рабочее место пользователя):

\begin{itemize}
      \item устройство с современным веб-браузером и поддержкой JavaScript;
      \item соединение с интернетом для загрузки Яндекс Карт и обращения к API.
\end{itemize}

\subsection{Требования к программному обеспечению}

Для развeртывания серверной части с использованием Docker необходимо наличие:

\begin{itemize}
      \item операционной системы Linux, macOS или Windows с поддержкой контейнеризации;
      \item Docker Engine версии 24.0 и выше;
      \item Docker Compose версии 2.0 и выше.
\end{itemize}

При запуске серверной части без Docker дополнительно требуются:

\begin{itemize}
      \item Go версии 1.23 и выше;
      \item PostgreSQL версии 16 с расширением PostGIS версии 3.4;
      \item утилита \texttt{migrate} для применения миграций.
\end{itemize}

Для сборки и запуска клиентской части в режиме разработки необходимы:

\begin{itemize}
      \item Node.js версии 18 и выше;
      \item менеджер пакетов pnpm версии 8 и выше (либо npm версии 9 и выше).
\end{itemize}

На стороне пользователя поддерживаются следующие браузеры:
Google Chrome версии 90 и выше, Mozilla Firefox версии 88 и выше,
Apple Safari версии 14 и выше, Microsoft Edge версии 90 и выше.

\section{Руководство пользователя и администратора}

\subsection{Общие сведения о развeртывании}

Приложение состоит из двух независимо запускаемых компонентов:
серверной части (Go API + PostgreSQL) и клиентской части (React SPA).
Серверная часть распространяется в виде Docker-образов и предназначена
для запуска на сервере или локальной машине.
Клиентская часть запускается в веб-браузере и не требует установки
дополнительного программного обеспечения на стороне пользователя.

Поддерживаются следующие платформы для развeртывания серверной части:
Linux (рекомендуется), macOS и Windows с установленным Docker Engine.

\subsection{Установка и настройка серверной части}

\subsubsection{Развeртывание с использованием Docker Compose}

Рекомендуемым способом развeртывания является использование Docker Compose,
который автоматически поднимает все необходимые сервисы: базу данных PostgreSQL
с расширением PostGIS, службу применения миграций и сам API-сервер.

Последовательность установки:

\begin{enumerate}
      \item Убедиться в наличии установленных Docker Engine (версии 24.0 и выше)
            и Docker Compose (версии 2.0 и выше).
      \item Перейти в директорию \texttt{backend/}.
      \item При необходимости изменить переменные среды непосредственно в файле
            \texttt{docker-compose.yml} или передать их через файл \texttt{.env}.
      \item Выполнить команду:
            \begin{verbatim}
docker compose up --build
          \end{verbatim}
\end{enumerate}

После выполнения указанных шагов Docker Compose последовательно:
запустит контейнер базы данных PostgreSQL,
дождeтся готовности СУБД (проверка через \texttt{pg\_isready}),
применит SQL-миграции через утилиту \texttt{migrate},
запустит API-сервер на порту 8080.

\subsubsection{Параметры конфигурации}

Конфигурация серверной части осуществляется через переменные окружения.
Перечень параметров приведeн в таблице~\ref{tab:env_vars}.

\subsubsection{Развeртывание без Docker}

При запуске серверной части без контейнеризации необходимо:

\begin{enumerate}
      \item Установить Go версии 1.23 и выше, PostgreSQL версии 16
            с расширением PostGIS версии 3.4, а также утилиту \texttt{migrate}.
      \item Создать базу данных и пользователя PostgreSQL с правами на неe.
      \item Скопировать файл конфигурации:
            \begin{verbatim}
cp .env.example .env
          \end{verbatim}
            и заполнить параметры \texttt{APP\_DB\_DSN} и \texttt{APP\_JWT\_SECRET}.
      \item Применить миграции вручную:
            \begin{verbatim}
migrate -path ./migrations -database "<DSN>" up
          \end{verbatim}
      \item Запустить сервер:
            \begin{verbatim}
make run
          \end{verbatim}
\end{enumerate}

\subsection{Установка и настройка клиентской части}

\subsubsection{Режим разработки}

Для запуска клиентского приложения в режиме разработки необходимо:

\begin{enumerate}
      \item Убедиться в наличии Node.js версии 18 и выше,
            менеджера пакетов pnpm версии 8 и выше (либо npm версии 9 и выше).
      \item Перейти в директорию \texttt{frontend/Task Planning App/}.
      \item Создать файл \texttt{.env.local} и указать ключ Яндекс JS API:
            \begin{verbatim}
VITE_YANDEX_GEOCODER_KEY=<ключ>
          \end{verbatim}
            Ключ необходимо получить на портале разработчиков Яндекса,
            подключив сервис <<JavaScript API и HTTP Геокодер>>.
            Активация ключа занимает до 15~минут после регистрации.
      \item Установить зависимости и запустить сервер разработки:
            \begin{verbatim}
pnpm install
pnpm dev
          \end{verbatim}
\end{enumerate}

Приложение будет доступно по адресу \texttt{http://localhost:5173}.
Все запросы к адресам вида \texttt{/api/*} автоматически проксируются
на серверную часть по адресу \texttt{http://localhost:8080}
через встроенный механизм Vite.

\subsubsection{Сборка для продуктивной эксплуатации}

Для получения оптимизированной статической сборки выполняется команда:

\begin{verbatim}
pnpm build
\end{verbatim}

Собранные файлы размещаются в директории \texttt{dist/} и могут быть
опубликованы на любом веб-сервере (Nginx, Apache, Caddy и других).
При этом необходимо настроить перенаправление всех запросов
на файл \texttt{index.html} для корректной работы клиентской маршрутизации,
а также проксирование запросов к API на серверную часть.

\subsection{Краткое руководство пользователя}

Для начала работы с приложением пользователю необходимо:

\begin{enumerate}
      \item Открыть приложение в браузере и зарегистрироваться,
            указав адрес электронной почты и пароль,
            либо войти в существующую учeтную запись.
      \item На главной странице нажать кнопку добавления задачи.
            В открывшемся модальном окне ввести название задачи,
            адрес выполнения, продолжительность и временное окно (при необходимости).
      \item После добавления нескольких задач нажать кнопку
            <<Оптимизировать маршрут>>.
            Приложение выполнит геокодирование адресов,
            получит матрицу расстояний и вычислит оптимальный порядок задач.
      \item Результат отображается одновременно в списке задач (в оптимальном порядке)
            и на карте (в виде маршрутной линии с пронумерованными метками).
      \item При необходимости пользователь может вручную изменить порядок задач
            методом перетаскивания карточек.
      \item Для удаления или редактирования задачи следует воспользоваться
            соответствующими элементами управления на карточке задачи.
\end{enumerate}

\subsection{Руководство администратора}

Администратор системы несeт ответственность за развeртывание,
поддержание работоспособности и обновление серверной части приложения.

\textbf{Резервное копирование.}
Данные PostgreSQL хранятся в именованном томе Docker \texttt{db\_data}.
Для создания резервной копии следует использовать утилиту \texttt{pg\_dump}:

\begin{verbatim}
docker exec <container_db> pg_dump -U planner planner > backup.sql
\end{verbatim}

Восстановление из резервной копии:

\begin{verbatim}
docker exec -i <container_db> psql -U planner planner < backup.sql
\end{verbatim}

\textbf{Обновление приложения.}
При выходе новой версии необходимо пересобрать образы командой
\texttt{docker compose up --build}, которая автоматически применит
новые миграции базы данных перед запуском сервера.

\textbf{Мониторинг.}
Состояние контейнеров отслеживается командой \texttt{docker compose ps},
журналы приложения~--- командой \texttt{docker compose logs api}.

\textbf{Обеспечение безопасности.}
В продуктивной среде необходимо:
заменить все пароли по умолчанию в \texttt{docker-compose.yml},
установить значение \texttt{APP\_JWT\_SECRET} равным криптографически
стойкой случайной строке,
ограничить доступ к портам 5432 и 8080 на уровне межсетевого экрана,
предоставив внешний доступ только к порту 8080 (или разместив
приложение за обратным прокси-сервером с поддержкой TLS).

\subsection{Вывод}

Приложение поддерживает два способа развeртывания серверной части:
с использованием Docker Compose (рекомендуется) и без контейнеризации.
Docker Compose обеспечивает автоматическое применение миграций и изоляцию
зависимостей, что упрощает как первоначальную установку, так и дальнейшее
обслуживание системы.

Руководство пользователя описывает полный цикл работы с приложением,
а руководство администратора охватывает процедуры резервного копирования,
обновления и обеспечения безопасности, необходимые для продуктивной эксплуатации.
