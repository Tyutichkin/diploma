\section{Анализ внедрения продукта}

В первой главе сформулированы цель разработки и перечень функциональных и
нефункциональных требований к системе.
В данном разделе проводится сопоставление этих требований с результатами реализации.

Все сформулированные функциональные требования реализованы в полном объеме.
Полное соответствие реализации перечню требований приведено в
таблице~\ref{tab:requirements_check}; ниже перечислены технические решения,
которые не очевидны из её строк.

Матрица расстояний формируется двумя путями: в основном сценарии клиент
рассчитывает её через мультимаршрутизатор Яндекс JavaScript API и HTTP
Геокодер~\cite{yandex_maps_js_api} и передаёт серверу в теле запроса на
оптимизацию, что согласует данные оптимизации с маршрутом, отображаемым
на карте; при отсутствии клиентской матрицы сервер строит её через свободный
сервис OSRM~\cite{osrm,luxen2011osrm}. Полученные значения кэшируются на
уровне приложения в оперативной памяти для повторного использования между
запросами.

Алгоритм оптимизации помимо временных окон поддерживает фиксированные
начальную и конечную точки маршрута, а также попарные ограничения порядка
посещения, рассчитывая для каждой остановки время прибытия, начала и окончания
обслуживания.

Нефункциональные требования также выполнены.
Серверная часть реализована на языке Go с использованием HTTP-фреймворка Gin.
Go компилируется в нативный исполняемый файл, а модель конкурентности на основе горутин
позволяет обслуживать множество одновременных соединений без выделения отдельного потока
операционной системы на каждый запрос \cite{saioc2023goroutine}.
Требование по времени ответа обеспечивается за счет использования пула соединений
драйвера \texttt{pgx/v5}, кэширования матрицы расстояний в оперативной памяти
приложения и вычисления матрицы на клиентской стороне через мультимаршрутизатор
Яндекс JavaScript API и HTTP Геокодер~\cite{yandex_maps_js_api},
что снижает нагрузку на сервер при оптимизации.
Устойчивость к повторным запросам к внешним API обеспечивается кэшем в
памяти приложения (\texttt{CachedProvider} на основе библиотеки
\texttt{hashicorp/golang-lru/v2}~\cite{golang_lru}, пакет \texttt{expirable}):
при наличии ранее вычисленного значения между парой точек обращение к OSRM
не производится.
Контейнеризация на основе Docker Compose обеспечивает воспроизводимость
развертывания и независимость от конфигурации целевого сервера.
Поддержка современных браузеров обеспечивается выбором клиентского стека
(React~18 + Vite~6 + TypeScript): согласно официальной документации,
React~18 поддерживает все браузеры, совместимые с ES2015~\cite{react},
а Vite~6 нацеливается на браузеры с поддержкой нативных ES-модулей~\cite{vite}
(Chrome~89+, Firefox~89+, Safari~15+, Edge~89+).

\section{Аспекты отказоустойчивости, надежности и производительности}

\subsection{Устойчивость к отказам внешних зависимостей}

Одним из ключевых рисков систем, интегрирующих внешние сервисы, является
деградация или временная недоступность стороннего API.
В разработанном приложении этот риск снижается на двух уровнях.

На уровне приложения реализован кэш значений расстояния и времени
перемещения между парами географических точек (\texttt{CachedProvider}
над интерфейсом \texttt{distance.Provider}).
В качестве хранилища используется библиотека \texttt{hashicorp/golang-lru/v2}
(пакет \texttt{expirable})~\cite{golang_lru} --- потокобезопасный LRU-кэш
с ограниченным размером и временем жизни записи, что исключает
неконтролируемый рост занимаемой памяти.
При наличии записи в кэше сервер не выполняет повторного обращения к OSRM.
Это снижает зависимость от доступности внешнего маршрутизатора и уменьшает
суммарную задержку при повторных оптимизациях маршрутов с теми же точками.

На уровне пользовательского интерфейса загрузка Яндекс JS API реализована
через утилиту \texttt{loadYandexMaps()}, которая инжектирует \texttt{<script>}-тег
динамически при первом обращении и возвращает один и тот же Promise при
последующих вызовах (одиночный экземпляр).
Такой подход предотвращает дублирующую загрузку скрипта при одновременном
обращении нескольких компонентов и исключает состояние гонки при инициализации API.

\subsection{Надежность аутентификации}

Аутентификация реализована по схеме JWT~\cite{rfc7519} с двумя токенами:
краткосрочным \texttt{access}-токеном (время жизни~— 15~минут) и
долгосрочным \texttt{refresh}-токеном (время жизни~— 30~дней).
Применение пары access/refresh-токенов соответствует общему подходу
к делегированной авторизации, описанному в~\cite{rfc6749oauth}.
Токены обновления хранятся в базе данных в виде хэша SHA-256,
что исключает их компрометацию при несанкционированном доступе к СУБД;
данная мера согласуется с практическими рекомендациями по защите
сервисов, использующих JWT~\cite{devitsyna2023jwt}.
Пароли пользователей хэшируются алгоритмом \texttt{bcrypt}~\cite{provos1999bcrypt}
с адаптивным количеством раундов.

На клиентской стороне реализован механизм автоматического обновления токена
при получении ответа с кодом 401. Корректность этого механизма проверяется
модульными тестами API-клиента с перехватом HTTP-запросов через Mock Service
Worker (MSW).
Для исключения множественных одновременных запросов на обновление применяется
дедупликация: при первом истечении токена запускается единственный запрос
обновления, остальные запросы ожидают его завершения через общий Promise.
После успешного обновления исходный запрос повторяется автоматически —
пользователь не замечает прерывания сессии.

Сессия пользователя сохраняется в \texttt{localStorage} под ключом
\texttt{planner.auth.session}.
При закрытии и повторном открытии браузера приложение автоматически
восстанавливает состояние аутентификации без повторного ввода учетных данных.

\subsection{Надежность инфраструктуры}

При развертывании с использованием Docker Compose~\cite{docker} зависимость между контейнерами
управляется через механизм \texttt{healthcheck}: сервис применения миграций и
API-сервер запускаются только после того, как контейнер базы данных PostgreSQL
подтвердит готовность к приему соединений командой \texttt{pg\_isready}.
Это исключает ситуацию, при которой API-сервер стартует до завершения инициализации СУБД.

Схема базы данных управляется инструментом \texttt{migrate/migrate},
запускаемым автоматически при каждом старте стека.
Применение миграций является идемпотентным: повторный запуск \texttt{migrate up}
при уже актуальной схеме не вносит изменений.
Это позволяет безопасно перезапускать стек без ручного контроля состояния миграций.

\subsection{Производительность}

Производительность серверной части обеспечивается несколькими механизмами.
Язык Go компилируется в нативный исполняемый файл, что устраняет накладные расходы
интерпретируемых сред.
Драйвер \texttt{pgx/v5} использует пул соединений к PostgreSQL,
исключая создание нового соединения на каждый HTTP-запрос.
HTTP-фреймворк Gin применяет \texttt{httprouter} с маршрутизацией на дереве-префикса
(radix tree), обеспечивая постоянное время поиска маршрута вне зависимости
от числа зарегистрированных обработчиков HTTP-запросов.

Вычисления матрицы расстояний при оптимизации маршрута выполняются
на стороне клиента посредством Яндекс JS API,
что разгружает сервер от вычислительно емких операций и
позволяет обслуживать большее число одновременных пользователей
без изменения аппаратной конфигурации.

Требование нефункциональных характеристик об устойчивости к ограничениям
внешних API выполнено за счет кэша расстояний в памяти приложения:
при повторных оптимизациях маршрутов с теми же парами точек обращения
к OSRM из серверной части не производятся.

\subsection{Нагрузочное тестирование}

Для проверки нефункционального требования о масштабируемости до 100~одновременных
пользователей проведено нагрузочное тестирование REST API с использованием
инструмента k6~\cite{k6};
Тест воспроизводил типовой сценарий работы пользователя: аутентификация,
получение списка задач (\texttt{GET /api/tasks}) и создание новой задачи
(\texttt{POST /api/tasks}).
Каждый сценарий выполнялся в течение 60~секунд при фиксированном числе
виртуальных пользователей (VU).
Тестовый стенд: ноутбук с процессором Apple M2 (8~ядер), 16~ГБ оперативной памяти,
серверный стек запущен локально через Docker~Compose.
Критерии успешности: 95-й процентиль времени ответа менее 2000~мс,
доля ошибочных HTTP-ответов менее 1\,\%.

\subsection{Вывод}

Нагрузочное тестирование подтвердило выполнение требования масштабируемости:

\section{Внедрение и сопровождение программного продукта}

\subsection{Модель распространения}

Разработанное приложение является веб-приложением с клиент-серверной
архитектурой и не требует установки специализированного программного обеспечения
на рабочее место конечного пользователя.
Пользователь взаимодействует с системой через стандартный веб-браузер.

Серверная часть распространяется в виде исходного кода и \texttt{Dockerfile},
что позволяет развернуть приложение на любой платформе с поддержкой Docker
(Linux, macOS, Windows).
Клиентская часть собирается в набор статических файлов (HTML, CSS, JavaScript)
командой \texttt{pnpm build} и публикуется на любом веб-сервере
(Nginx, Apache, Caddy и др.) без дополнительных зависимостей времени исполнения.

\subsection{Процедура первоначального развертывания}

Рекомендуемым способом развертывания является Docker Compose.
Подробные инструкции по установке, конфигурированию и типичным затруднениям
приведены в разделе~<<Руководство пользователя и администратора>> второй главы.
Перед переходом в продуктивную эксплуатацию необходимо обязательно изменить
учетные данные СУБД, установить криптографически стойкое значение переменной
\texttt{APP\_JWT\_SECRET} и задать корректный адрес клиентской части в
переменной \texttt{APP\_CORS\_ORIGINS}.

\subsection{Сопровождение и обновление}

Обновление, резервное копирование и мониторинг выполняются стандартными средствами Docker.
Процедуры обновления (команда \texttt{docker compose up --build}), создания резервных копий
(\texttt{pg\_dump}) и контроля состояния контейнеров подробно описаны в руководстве
администратора второй главы.

\subsection{Ограничения и направления развития}

В текущей реализации хранение географических координат задач в базе данных
осуществляется в соответствии с условиями бесплатного тарифа Яндекс JS API,
которые допускают это для учебных и некоммерческих проектов.
Для продуктивного использования в коммерческой среде потребуется переход
на коммерческую лицензию API.

Суточный лимит бесплатного тарифа составляет 1~000~запросов к геокодеру
и 25~000~запросов к JavaScript API.
При превышении указанных лимитов рекомендуется рассмотреть переход
на коммерческий тариф либо интеграцию с альтернативным геокодером.

Среди перспективных направлений развития системы можно выделить:

\begin{itemize}
      \item реализацию фоновых уведомлений о наступлении временного окна следующей задачи;
      \item поддержку командной работы с общим пулом задач;
      \item интеграцию с внешними календарями (Google Calendar, Яндекс Календарь);
      \item расширение алгоритма оптимизации более мощными метаэвристиками
            (муравьиный алгоритм, генетический алгоритм) для повышения качества
            решений при большом числе задач;
      \item учет реального дорожного трафика при построении матрицы расстояний.
\end{itemize}

\section{Выводы}

В настоящей главе рассмотрены вопросы внедрения и опытной эксплуатации
разработанного приложения. Выполнен анализ соответствия реализованной
программной системы функциональным и нефункциональным требованиям,
сформулированным в первой главе, и подтверждено, что все ключевые
требования выполнены: реализованы регистрация пользователей и защищенная
аутентификация, ведение списка задач с временными окнами, автоматическое
построение оптимальной последовательности их выполнения, визуализация
маршрута на карте, импорт и экспорт списка задач.

Описаны принятые архитектурные решения, обеспечивающие отказоустойчивость
и надежность работы системы: использование контейнеризации, применение
обратимых миграций базы данных, автоматическое восстановление сессии
пользователя после истечения срока действия токена доступа,
а также защищенное хранение паролей и обработка ошибок взаимодействия
с внешними сервисами. По результатам нагрузочного тестирования установлено,
что система обеспечивает приемлемые показатели производительности
при типовой нагрузке, а 95-й процентиль времени отклика не превышает
заданного порога.

Подготовлены и описаны процедуры развертывания, резервного копирования
и обновления, обеспечивающие штатное сопровождение системы в продуктивной
среде. Определены текущие ограничения реализации, связанные с условиями
лицензирования внешних картографических сервисов, а также сформулированы
перспективные направления дальнейшего развития, среди которых
интеграция с внешними календарями, поддержка совместной работы и
применение более мощных метаэвристик при большом числе задач.

Полученные результаты подтверждают практическую применимость
разработанного решения и его готовность к опытной эксплуатации.
